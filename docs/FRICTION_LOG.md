# Opportunities to improve

This log records behavior observed while building, tracing, and preparing to evaluate the grocery agent. It separates evidence from proposed product responses.

| Workflow | Expected | Observed | Product impact | Evidence | Candidate response |
| --- | --- | --- | --- | --- | --- |
| Trace setup | A completed run appears in the intended project with agent, model, and tool spans. | The application initially completed requests while the project appeared empty. The export endpoint, space, project, key, and environment had to be validated separately. | Time to first useful trace increases because the developer cannot immediately distinguish routing, credentials, ingestion, selection, or app failure. | Subsequent successful trace in `arize-grocery-agent`. | Provide one diagnostic connection test with export status and a direct link to the received trace. |
| Failed-run visibility | Completed model and tool work remains available when the root workflow times out. | Two 15-second timeouts occurred before the Worker exported its reconstructed trace; Cloudflare logs held the decisive evidence. | The runs that most needed investigation were also the hardest to move directly into evaluation. | Reproduced timeout investigation; successful runs later reached Arize. | Encourage incremental or failure-safe export and render incomplete roots with an explicit terminal state. |
| Native evaluator mapping | A chosen template maps to valid semantic fields, or identifies missing fields before execution. | Templates were easy to find, but initial spans lacked evaluator-ready separation among request, evidence, answer, messages, tools, and trajectory. | An evaluator can run on unintended fields and produce a plausible score for a different question. | Native evaluator setup and enriched trace inspection. | Add a mapping preflight that inspects sample values, semantic overlap, scope, and missing OpenInference fields. |
| Trace to dataset | An observed failure becomes a reusable case without manual reconstruction. | `Add to Dataset` worked directly from selected root spans and preserved key input, output, version, latency, stop, and trajectory fields. | The core conversion path is present and useful. | Four observed cases added to `grocery-agent-regression-cases`. | Build on the existing action; do not propose duplicating it. |
| Dataset to experiment | The generated task contract matches the dataset, evaluator, operational, and lineage requirements of the release decision. | The code path assumed a `question` field that was absent; imported trace fields were nested; reference evidence was missing; token and cost summary cards were blank. | Individually valid mappings did not produce one complete record for deciding whether to promote, revise, or hold the candidate. | Dataset export and Run via Code workflow. | Extend existing mappings and previews with an Evaluation Readiness Preflight that validates the complete decision contract before the first scored run. |
| Mixed evaluator scope | One task can be composed from selected evaluators, or incompatible scopes are separated before submission. | A native task combining span- and trace-level evaluators failed only after submission. | The user discovers a predictable constraint late and must rebuild the task. | Arize CLI task creation. | Group selected evaluators by span, trace, and session scope in the builder. |
| Account capability | Evaluator availability is known before authoring and upload. | Custom code evaluator creation returned `Custom code evals are not available for your account` after the evaluator had been authored. | The developer must rework the evaluation through an alternate execution and import path. | Authenticated CLI creation attempt. | Surface entitlements at entry and document external-score import. |
| Operational and AI correlation | One identifier follows a customer action across OCR, app logs, model calls, tools, and outcome evaluation. | Cloudflare exposed runtime failures while Arize exposed successful AI traces; OCR and comparison are separate requests around human review. | Operators manually correlate the request across systems. | Worker logs, OCR endpoint, comparison endpoint, and Arize traces. | Propagate workflow, request, trace, span, and agent-run IDs across logs, metrics, and linked traces. |
| Exact trace readiness | A trace accepted by the platform shows whether it is complete or still indexing. | For one workflow, the first exact read returned 13 of 17 expected spans; a later read returned all 17. | A developer can diagnose or score a partial trajectory as though it were final. | [End-to-end evidence dashboard](OBSERVABILITY_DASHBOARD.md), “Trace-readiness finding.” | Compare returned spans with root-declared span count and parent links, then expose an indexing or complete state in trace-derived workflows. |
| Evaluator execution coverage | A task reports expected, successful, failed, and missing labels and supports retrying only failures. | Provider throttling left B with 37/44 labels and C with 36/44. A normal retry did no work; override reran successful labels too. | Developers may incur additional judge spend and still remain uncertain about whether the comparison is complete. | Native span- and trace-template task exports. | Add failed-only retry, explicit coverage state, and provider-capacity guidance before execution. |
| Evaluator context projection | Each evaluator receives only the fields needed for its question. | The full 14-item output exceeded one hallucination evaluator's context window. | A predictable mapping condition interrupts the run after judge work has started. | Prompt B/C native evaluator task logs. | Preview projected token size and support evaluator-specific structured field selection. |
| Semantic and deterministic disagreement | Quality scores reflect both fluent outcome judgment and hard execution invariants. | Native judges approved several Prompt C abstentions as relevant, factual, correct, or complete while deterministic checks found no usable evidence for expected products. | A coherent answer can receive a passing score even when a tool-contract failure removed the evidence needed for the customer decision. | Prompt C experiment runs and attached deterministic annotations. | Present semantic scores beside execution invariants and require explicit disagreement review before promotion. |
| Operational comparison | Latency, tokens, and errors appear automatically beside quality movement. | Experiment analysis offered operational columns, but the fields were blank even though the values existed in experiment outputs and source traces. | The UI can make a quality gain visible without making its operating cost equally visible. | Prompt B/C experiment analysis and verified exports. | Populate operational rollups from run output or provide a mapping step in the preflight. |

## What this changed in the product proposal

Arize already handles trace-to-dataset conversion, field mapping, and sample previews. The remaining opportunity is helping a developer determine whether the full experiment can support the intended release decision before spending time and judge calls. Part 2 adds a decision contract covering target outcome, quality and operating guardrails, compatible evaluator scope, context-safe projection, explicit score coverage, operational rollups, and version lineage.
